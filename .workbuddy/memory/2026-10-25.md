## [本地开发] 加法"理解"验证：查表 vs 生成

- **验证用户判断**：辉月 `transforms` 14 条，**无一条含"十"**；`transform_compose` 连跑 5 次全 None。
  即使喂到 `九加一→十`（9 条），仍推不出 `十加一→十一`——因为它的推导只是
  "把已知结果展开成操作数，再查 direct 表"，是**已有事实的组合闭包**，不是生成。
- **原型** `runs/number_sense.py`：只用 `succ`（加一个记号）+ `pred`（去一个记号）+ 递归定义
  `a+0=a`、`a+S(b)=S(a+b)` → 17+15=32（15 步）、999+1=1000（1 步）、123+456=579（456 步）、
  32-15=17（逆运算）、17×3=51（重复加法）；`1+1=3` 判假并给出理由（链长 2 vs 3）。
  中文数字解析（十七/三十二/一百零五）也实现了，属"位值制理解"。
- **对照** `runs/peano_demo.py`：查表 N 条 → 最多 N 题；2 条规则 → 无限题 + 每步可验证。
- **结论**：理解 = 有限规则生成无限行为 + 可自我验证；差别不在"记不记"，在"记的是不是缓存"。
  辉月是"14 条事实 + 一个组合器"，没有"数感"这一层。
- **接入方案**：`number_sense` 放在 `transform_compose` 之前（先规则推 → 再查表 → 最后问大脑）；
  transforms 降级为缓存，必须能由规则重算校验。
- **诚实边界**：这是"弱理解"（人给规则），不是"强发现"（自己发现加法）。后者需集合/一一对应/基数守恒。

## [本地开发] 概念数据结构与"理解"讨论 + 原型

- 用户质疑 Peano 原型只是算法，不是理解。已公开认账：那版只满足"能力"，不满足"意义"。
- 把"理解"拆三层：能力（会算）/ 意义（知道指什么、何时该用）/ 体验（无法验证）。
  中文屋（Searle）与用户直觉一致；系统回复（理解是系统属性）也未决。工程上确定缺的是**接地**。
- **新原型** `runs/concept_demo.py`：概念生命周期五阶段——观察合并 → 提出不变式
  `count(merge(A,B)) = add(count(A),count(B))` → 新例验证（置信度 0.30→0.75）→ 17+15=32（不靠记忆）
  → 用于决策（能量 3 < 成本 5，缺 2，先休息）→ 判错（1+1=3 为假）。
- **文档** `docs/概念-数据结构草案.md`：Concept = ground(probe) + affordances + rules + history；
  思考 = 处境匹配 → 激活 → 调 probe → 用于决策 → 回写置信度；LLM 只做翻译/类比/提探针/解释，
  不存概念、不判真伪、不当决策器。
